# MOSS 62994 训练退步原因分析

本次退步主要表现为**长输出的重复生成、说话人标签格式漂移，以及解析器对局部错误恢复不充分**。这些问题造成大量文字和语音区间在正式评分中缺失。训练数值精度是新发现的高优先级疑点；现有证据还不能确定是学习率、训练轮数或精度中的哪一项触发了输出失稳。

本分析使用已校验的全部 164 条原始预测与逐会议指标，并通过 SSH 只读核对了训练入口、536 条训练目标、优化器元数据。未重新训练、重新生成预测或修改正式评分。下文的语法恢复与后验子集比较仅用于诊断。

## 1. 总分退步高度集中于少数失败会议

cpCER 是按说话人匹配后累计的字符错误率。下表将每组全部会议的 cpCER 增量拆成互斥部分，分母始终使用该组全部参考字符数。

| 数据 | cpCER 总变化 / 百分点 | 截断会议的贡献 | 无截断但严重格式失效的贡献 | 其余会议贡献 |
|---|---:|---:|---:|---:|
| AliMeeting test，20 场 | +17.66 | 5 场，+15.02 | 0 | 15 场，+2.63 |
| AISHELL-4 test，20 场 | +9.43 | 1 场，+2.78 | 2 场，+6.13 | 17 场，+0.52 |
| AMI dev，18 场 | +25.77 | 1 场，+4.71 | 4 场，+22.51 | 13 场，−1.45 |
| AliMeeting dev，8 场 | +16.59 | 2 场，+11.58 | 1 场，+5.13 | 5 场，−0.12 |
| AMI test，16 场 | −7.14 | 0 | 0 | 16 场，−7.14 |

独立四舍五入会使表内分量相加差 0.01；未舍入值已经逐组对齐。AliMeeting test 的 5 场截断贡献 31,523 / 37,050 = **85.1%** 的净 cpCER 错误增量。AISHELL-4 test 的 3 场异常贡献 16,090 / 17,037 = **94.4%**。AMI dev 的 5 场异常贡献超过净增量，因为其余会议的改善抵消了一部分损失。

“严重格式失效”的诊断定义为：未截断，独立合法片段扫描得到的规范化文字量超过现有解析器的两倍，且超过 100 字符。这是根据模型输出制定的后验分类，并非新的评估排除规则。分类包括非标准说话人标签、额外括号和解析失步，不能把该组全部损失都归因于解析器实现。

其余子集仍显示真实残余退步：AliMeeting test 剩余 15 场 cpCER 为 **9.76% → 13.56%**；AISHELL-4 test 剩余 17 场为 **14.77% → 15.38%**。另一方面，AMI dev 剩余 13 场为 **11.25% → 9.16%**，AMI test 中 12/16 场 cpCER 改善。因此，整体情况不能用“所有会议的识别能力都下降”概括。上述子集是结果发生后的描述，不是剔除失败样本后的新正式成绩。

## 2. 截断大多是重复生成耗尽预算

9 条截断输出的末尾均存在持续重复：汉字、短语或时间戳循环。已看到的连续相同 token 最长记录包括：

- AliMeeting dev `R8001_M8004`：同一 token 连续 **60,013** 次，尾部为“你”的循环。
- AliMeeting test `R8004_M8006`：同一 token 连续 **61,812** 次，尾部为“那”的循环。
- AISHELL-4 test `L_R003S04C02`：同一 token 连续 **62,098** 次，尾部为“这”的循环。

这些输出达到 65,536 token 上限，但最后有效解析时间分别只覆盖约 33.5%、12.0%、23.1% 的音频时长。这里的“最后解析时间 / 音频时长”是进度线索，不等于语音覆盖率。其余重复样本见逐会议明细。

提高生成上限并不能让这些循环自动恢复；它可能只增加运行时间。原始模型在同一输入、预算和贪心解码下没有截断。问题已经存在于训练后权重的自由生成行为，不能仅归咎于预算。

## 3. 只统计空解析会漏掉大量格式失败

此前报告统计了 2 条空解析，但本次发现还有多条“只解析出前几个片段”的结果。典型案例：

| 会议 | 生成现象 | 正式解析片段数 | 独立合法片段扫描数 |
|---|---|---:|---:|
| AMI dev `TS3004b` | 开头重复 `[34.65][34.65]` | 0 | 503 |
| AMI dev `IB4011` | 正常 EOS，后文存在大量合法片段 | 7 | 444 |
| AMI dev `TS3004d` | 出现 `[[S02]` 等额外左括号 | 1 | 759 |
| AliMeeting dev `R8009_M8020` | 前段之后解析失步 | 423 | 829 |
| AISHELL-4 test `M_R003S05C01` | 841 次 `[MULTI]`，不符合 `[Sxx]` | 2 | 10 |

`IB4011` 的原始文字一直延伸到约 2,386 秒，正式解析却只到 36.94 秒。这属于生成格式错误与解析恢复策略共同放大的失效。`MULTI`、`Kathryn` 等标签本身不符合本次格式约定，即便解析器恢复，也不能凭空还原成正确说话人身份。

已经用一个三片段的最小样例复现解析器失步：中间多一个时间戳后，原解析器只返回第一段，之后合法的两段也丢失。该复现不涉及模型、音频或参考答案，直接证实解析器恢复行为的影响。

进一步对所有原始文本运行独立严格片段扫描：只读取现有合法的 `[时间][S数字]文字[时间]` 块，不创造或替换文字、说话人编号、时间戳。原始模型全部 82 场的 CER/cpCER 不变；SFT 有 10 场分数变化。

| 数据 | 原始模型正式 cpCER | SFT 正式 cpCER | SFT 语法恢复诊断 cpCER |
|---|---:|---:|---:|
| AliMeeting dev | 14.74% | 31.33% | 26.21% |
| AMI dev | 10.72% | 36.49% | 23.01% |
| AliMeeting test | 15.32% | 32.98% | 27.36% |
| AISHELL-4 test | 15.08% | 24.51% | 22.44% |
| AMI test | 16.42% | 9.28% | 9.28% |

**解析器会放大退步，但修复解析恢复仍不足以消除退步。**诊断扫描也会跳过不合法编号及包含不符合其语法的方括号文字，因此这些分数不是最优恢复结果，更不是可以替换正式成绩的分数。

## 4. 训练实现中最值得验证的疑点：更新精度

实际入口先以 `dtype=torch.bfloat16` 加载模型，再交给原生 AdamW；没有 FP32 主权重或其他补偿更新路径。`checkpoint-402/optimizer.pt` 的元数据确认：683 组参数的 `exp_avg` 和 `exp_avg_sq` 全部为 **BF16**，只有步数为 FP32。不能把这个设置理解成仅在矩阵乘法中使用 BF16 的混合精度。

在 BF16 参数上直接写回很小的更新，可能被舍入抵消。该机制已有原始研究证明会影响优化进展与精度：[Revisiting BFloat16 Training](https://arxiv.org/abs/2010.06192)。PyTorch 的混合精度做法把低精度用于合适的计算，而保留需要的高精度路径：[AMP recipe](https://docs.pytorch.org/tutorials/recipes/recipes/amp_recipe.html)。

本次将交叉熵转换为 FP32，只提高损失计算精度，不能补偿 BF16 参数或优化器状态中已经损失的更新信息。因此建议把“FP32 权重与优化器状态 + BF16 前反向计算”的对照放在最高优先级。

**证据边界：BF16 配置是已确认事实，其对本次退步的因果贡献尚未确认。**目前没有保持其他条件相同的 FP32 更新对照，也没有记录逐参数更新被舍入的比例，不能直接宣称它就是唯一根因。

## 5. 无验证集监控使问题直到训练结束才暴露

真实配置为：3 epochs、402 步、有效 batch=4 场完整会议、初始学习率 1e-5、线性衰减、warmup=0、weight_decay=0、全参数更新、`eval_strategy=NO`。训练检查点只保留最近两个，现存 400 和 402 步，无法据此定位最早何时出现退步。

训练 loss 的每轮平均 0.4409 → 0.4267 → 0.4248 来自输入正确历史文本的监督训练。正式评估则让模型使用自己刚生成的历史继续输出。前者的平均值下降，不能保证后者能连续维持正确文字、说话人标签和终止行为。

缺少验证集自由生成、格式通过率、重复率与 best checkpoint 选择，是本次流程的明确缺口；它解释了为何没能及早发现并保留较好的阶段，但不证明更早的检查点必然更好。“学习率太高”“3 轮导致过拟合”都需要对照，不能由这一个最终权重确认。

此前的工程检查覆盖 loss/梯度等价、显存与保存恢复，未覆盖多步更新的数值精度和中途自由生成稳定性，后续应补上这两类验收。

## 6. 已检查但暂不支持的解释

- **训练目标直接含坏格式**：全部 536 条、355,402 个目标片段通过语法扫描及原解析器一致性检查；没有倒置/零时长片段或不合法说话人标签。此检查只覆盖结构，未人工复核全部音频与转写的语义正确性。
- **重复标签直接教会了六万 token 循环**：训练目标连续相同字符最长为 12，没有同量级循环的直接证据。
- **英语数据压倒中文**：监督 token 占比为 AliMeeting 51.15%、AISHELL-4 27.92%、AMI 20.93%；没有“英语占大多数”的证据。该占比本身也不能解释语料间效果差异。
- **动态 KV Mask 或 R-SWA 不兼容**：本次未启用这些方法，训练与评估均为 full attention、SP=1。
- **训练输入超过上限被截断**：全量预检最大 116,527 token，低于 131,072；标签包含 EOS，未发现训练样本被截断。
- **训练崩溃或普遍梯度爆炸**：全部 402 步 loss/梯度有限，无 OOM/NCCL 失败；15 步梯度范数超过裁剪阈值 1，最大约 5.97。没有普遍非有限值的证据，但数值舍入问题不要求先出现 NaN。
- **训练/推理提示顺序不一致**：训练整理器与推理调用同一 `build_transcription_messages`，训练文件中的 text/audio 行次序在整理后统一；训练提示文本也一致。

## 7. 下一步应怎样验证

1. 保留本次全部正式结果。先给解析器增加局部格式错误后的恢复及明确的失读告警，用最小样例和原有正常输出做回归检查。以独立协议版本报告结果，两模型共同重评分，不能只改 SFT 或覆盖本次分数。
2. 做短程数值精度对照：同一原始模型、数据顺序、学习率与固定步数，仅改变 FP32 参数/优化器更新路径；前反向仍可使用 BF16。比较若干训练更新的损失、参数变化及固定验证集自由生成，先判断精度是否影响输出稳定性。
3. 每 25–50 步检查固定验证集，记录 CER/cpCER/DER、重复/截断、非法标签和解析覆盖；保留起始及较早检查点和验证集最佳权重。若精度对照仍失败，再分别对照学习率、warmup 或冻结音频编码器，避免同时改多项而无法归因。
4. 基线稳定后再推进既定 RSWA 实验。不要依据本次测试集逐会议表现调参；新的选择依据应来自验证集，测试集留作最终确认。

本轮仅完成原因分析与只读诊断，尚未执行上述修复或对照训练。
