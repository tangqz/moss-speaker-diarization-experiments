# MOSS 下一轮 full attention SFT：实验依据、训练协议与后续对照

日期：2026-09-12。正式下一轮状态：**已完成设计，尚未提交完整训练**。

建议从原始 MOSS base 重新开始，保留完整会议、原始标注格式、全参数训练和普通 next-token 交叉熵。主要变化是**FP32 参数与优化器更新、分层验证、检查点选择与可复用的诊断记录**。这些是 full attention、KV mask SFT 和熵 RL 共同使用的训练基础设施。

本方案沿用《A40_动态RSWA与熵门控RL_兼容性评估_2026-09-11.md》的 DDP=4、SP=1 路线。当前生产参照是原始处理器、完整会议、缓存贪心解码和结构化说话人转写；没有引入专门针对已知失败会议的生产分支。

## 2. 已完成的小实验

### 2.1 监督、因果性与停止路径

- 人工可核算序列：自定义 loss 与逐位置独立 next-token 参照均为 0.0000370138，梯度一致；故意使用当前位置监督时 loss 为 9.4865。这项参照不复用原来的 shift 函数。
- 全部 536 条训练文本：分别编码 prompt/target 与拼接编码完全一致，未发现文本边界合并导致的标签错位。
- 真实短音频：首个目标位于 173，使用 query 172 预测；目标文本与 EOS 对应正确。官方 loss 与独立逐位置计算差约 5.96×10⁻⁸。
- 修改未来 16 个输入 token 后，较早 logits 最大变化为 0。
- 短音频 3 个位置、长前缀 8 个位置的缓存与完整重算均给出相同 top-1。BF16 logits 并非逐位相等，长前缀 RMS 差最大约 0.079；因此这不是所有长度、所有位置的缓存一致性证明。
- 保存和重载生成配置后，强制 EOS 实验在生成 151645 后结束。SFT 配置中重复列出的同一个 EOS ID 没有改变其含义；旧正式评估也显式使用了原始 EOS/pad。
- 小张量可见性参照验证了 full causal 与足够大窗口的一致、reference 保留及 future 隔离。尚未实现或验收生产级稀疏 KV 后端。

原始记录：`evidence-63400/contracts.json`。所有检查均有明确覆盖范围；尤其未来不变性目前是短序列实测。

### 2.2 重复起点回放

使用 AliMeeting dev 的 `R8001_M8004` 与 `R8003_M8001`，保留各自完整音频，以及旧 SFT 输出进入最长单 token 循环之前的 5,523 / 10,950 个 token。分别附加 k=0、1、2、4、8、16、32 次重复，比较 base 与旧 SFT-402。

例如 k=8：

| 会议 | base 重复 token 排名 / margin | SFT-402 排名 / margin |
|---|---:|---:|
| R8001_M8004 | 2 / −1.375 | 1 / +0.375 |
| R8003_M8001 | 2 / −0.250 | 1 / +2.125 |

SFT 在两个样例的 k=1、2、4、8、16、32 六个检查点都把重复 token 排在第一；base 在部分检查点改选其他候选。它支持“某些错误前缀上的持续重复偏好增强”，没有证明自然错误恢复率下降了多少。

概率和熵都没有单调变化。例如 R8001 的 SFT 熵在 k=2/4 时约为 1.33/2.83 nats。后续熵 RL 必须实测各类错误的熵分布，不能把“循环”等同于“低熵”，也不能把高熵门控当作现成的反重复算法。

**边界：**这些是两个已知 dev 失败样例，不是总体样本。整段前缀预填与原始逐 token 生成有 BF16 路径差异；R8001 在 k=0 的 SFT 重复 token 排第二，本实验不能定位原始轨迹精确的首次分叉。没有在本轮新实验中使用 test 样本调参。

图：`figures/prefix_replay.png`；逐点数据：`evidence-63399/replay.json`。

### 2.3 两条短程训练轨迹

两条轨迹都从同一原始 base 开始，seed=0，同一 16 场完整训练会议、329,169 个监督 token；每步有效 batch=4，共 4 步。实际执行为单卡累积 4 次，保持全模型可训练、full attention、学习率 1e-5、无 warmup、无 weight decay、梯度裁剪 1。学习率衰减的总长度仍是 **402 步**，没有把 4 步小实验重新压缩成一个衰减到零的周期。

| 路径 | 持久参数 / 梯度 / Adam 状态 | 前向计算 |
|---|---|---|
| A | BF16 | BF16 autocast，FP32 CE |
| B | FP32 | BF16 autocast，FP32 CE |

两者都启用保存激活到 CPU 的显存策略。更改持久参数 dtype 也可能影响层归一化、残差等中间计算；这组对照检验的是整套精度配置，不能把其差异全部归因于参数写回一个环节。

首步在 7 个组件各抽样 65,536 个参数位置，使用该轨迹实际裁剪后的梯度独立计算 FP32 Adam 首步参照。只在参照更新非零的位置统计“实际更新为零”：

| 组件 | BF16 路径 | FP32 路径 |
|---|---:|---:|
| 共享 embedding / 输出层 | 99.1% | 0.0% |
| LM 第 0 层 Q 投影 | 89.4% | 0.0% |
| LM 第 14 层 FFN | 87.4% | 0.0% |
| LM 第 27 层 FFN | 88.7% | 0.0% |
| 音频第 0 层 FFN | 80.2% | 0.0% |
| 音频第 23 层 FFN | 86.7% | 0.0% |
| 音频 adapter | 82.2% | 0.0% |

这把更新精度问题从配置疑点推进到了实际更新证据。比例只适用于这些组件的首步抽样，并非全部训练参数或全部 402 步的总体比例。[Revisiting BFloat16 Training](https://arxiv.org/abs/2010.06192)提供了相关舍入机制；本次直接记录的结果更接近实际实现。

保存后把两组权重都以相同 **BF16 推理路径**重载，完整音频、正确历史下的验证 loss 为：

| dev 会议 | base | A：4 步 BF16 更新 | B：4 步 FP32 更新 |
|---|---:|---:|---:|
| AMI IS1008a | 0.3902 | 0.3248 | **0.3060** |
| AliMeeting R8009_M8018 | 0.4433 | 0.3854 | **0.3653** |

训练时间为 A 414.1 秒、B 486.3 秒，B 增加约 17.4%；进程峰值显存为 11.69 / 19.30 GiB。这是单卡累积的 4 步实验，不是正式 DDP4 的吞吐预估。小实验最长样本为 61,920 token，未覆盖正式训练的最长 116,527 token。

另在 R8001 的同一错误前缀后附加 0/8/32 次重复，分别自由生成最多 64 token：**两个 4 步权重均没有继续原来的单 token 循环**。其中 k=8/32 的短续写基本一致。因此，短续写没有证明 FP32 在循环恢复上优于 BF16；也没有核验这些续写全部受到音频支持。其意义是提醒我们，初期检查通过仍不足以代替后续整场生成验证。

数值与图：`evidence_summary.json`、`update_audit.csv`、`validation_loss.csv`、`figures/update_writeback.png`、`figures/pilot_validation.png`。训练和重载记录分别位于 `evidence-63401`、`evidence-63402`。

## 3. 下一轮默认训练配置

| 项目 | 冻结配置 | 理由 |
|---|---|---|
| 初始化 | 原始 MOSS base，全参数训练，保留 tied embedding/head | 作为 base 的标准 SFT 对照 |
| 数据 | 原 536 场完整会议；原 prompt、processor、采样比例和标签；seed=0 | 保留长音频生产场景与后续对照的数据一致性 |
| Attention | full causal，SDPA，DDP=4、SP=1 | 与原路线一致 |
| 精度 | FP32 参数、梯度与 Adam 状态；BF16 autocast；FP32 CE | 已有实际更新和短程 loss 证据；可跨 SFT/RL 使用 |
| Batch | 每卡 1 场，4 卡，总 batch=4 | 维持旧配置及全局监督 token 归一化 |
| 优化器 | AdamW fused，lr=1e-5，β=(0.9,0.999)，eps=1e-8，clip=1 | 先保持学习率等因素固定，不把多个超参数变化混为一项 |
| 调度 | linear，总长度 402 步；warmup=0、weight decay=0 | 小实验尚未提供改变它们的证据；单独作为后续候选 |
| 最大预算 | 最多 3 轮 / 402 步，按验证选择和早停 | 不再默认最后一步就是最优模型 |
| 显存 | 原分块 CE、音频 FFN checkpoint；4 个 rank 均启用保存激活到 CPU | 为 FP32 常驻状态留空间，保持函数和目标不变 |
| 推理 | 两种训练精度最终均按 BF16、完整音频、原 EOS/pad、greedy、cache | 保持当前生产路径；不增加全局反重复限制 |

**第一段先运行至 134 步，完成第一轮完整验证后再按同一协议决定是否继续。**训练器从开始就按 402 步配置调度，阶段停止用 callback；恢复时保留 optimizer、scheduler、数据顺序和各 rank RNG。把 `max_steps` 临时改成 134 会改变学习率曲线，不符合本方案。

实现时应把 `parameter_dtype` 与 autocast 开关分开。仅在现有入口继续使用 `--bf16 true` 会触发原来的 BF16 权重加载，不能实现本方案。需在 Trainer 接管后、创建优化器后、首步更新后和恢复后断言持久参数及 Adam 状态均为 FP32。[PyTorch AMP recipe](https://docs.pytorch.org/tutorials/recipes/recipes/amp_recipe.html)是计算精度分工的参考。

CPU offload 是训练内存策略，不改变输入、注意力可见集合或损失。若实际四卡内存不足，先调整公共内存策略或验证 ZeRO；不通过缩短会议、缩小上下文或冻结音频编码器来悄悄改变基线。

## 4. 验证、选择与早停

### 分层频率

1. **每步：**loss 分子/有效 token 分母、学习率、梯度范数、显存、实际参数更新摘要。记录参数 dtype，不只记录 BF16 开关。
2. **每 25 步：**固定 6 场验证会议的完整音频 teacher-forced loss，以及分开的已知 dev 错误前缀诊断。loss 按监督 token 汇总，另报各语料和各 token 类型。
3. **第 50 步：**固定 6 场的完整自由生成，用于及早发现工程性或灾难性失稳；不能用短续写代替。
4. **第 134/268/402 步：**全部 26 场 dev 的完整自由生成，作为正式 checkpoint 选择依据。完整生成费用由真实长输出决定；不按目标文本长度缩短预算。

六场哨兵在每个 dev 语料中按时长排序，取下标 floor(q×(n−1))，q=0、0.5、1，时长相同时按 key 排序。选择规则只使用输入元数据，已冻结到 `sentinel_manifest.json`。这些 dev 会议以前已评估过，不能称为全新盲测；test 仍不用于本轮选择。AISHELL-4 当前没有独立 dev，本方案明确保留这一选择盲点，不把其 test 临时当作验证集。

### 指标与判定

每次完整验证记录 CER、cpCER、DER(collar 0 / 0.25)、漏检/误检/混淆、截断、空解析、严重解析失读、非法标签、重复跨度、实际 EOS、RTF 与峰值显存。保留每条原始输出，失败会议仍然参与正式评分。

主评分沿用原解析协议 v1，保持历史可比性。若加入鲁棒 parser，应冻结为独立版本、对所有模型共同重评分并并列报告；它不进入 SFT 损失，也不能把未生成的文本恢复出来。

选择分数预先定义为：各 dev 语料分别计算 `(cpCER% + DER0.25%)/2`，再对 AliMeeting、AMI 等权平均。语料内部仍使用原协议的累计参考字符/说话人时间分母，避免英语文本总量支配语料权重。

候选为 134/268/402 步中已经完成全量验证的权重。接受条件：全量完成、截断和空解析为 0、严重解析失读为 0；每个语料的 cpCER 和 DER0.25 相对 base 均不恶化超过 1 个百分点，并且总选择分数优于 base。严重失读沿用诊断定义：独立合法片段扫描得到的文字量大于原解析量两倍且超过 100 字符。

在合格候选中选最低分，差距在 0.1 个百分点内优先更早的权重。若连续两次完整验证比此前最佳分数差至少 0.5 个百分点，提前结束；第一轮也与 step-0 base 比较。这些阈值是事前工程判据，不是统计显著性声明。没有合格 SFT 时如实报告，不把剔除异常会议后的成绩当作验收结果。

每 25 步保留 FP32 权重；完整恢复状态保留最近两份以及完整验证节点和所选最佳节点。预留约 110 GiB 存储，启动前核对实际空间。避免再次只剩 400/402 两个相邻检查点。

## 5. 保持后续实验的因果可比性

| 要回答的问题 | 必须配对的实验 | 共享项 |
|---|---|---|
| KV mask 本身改变了什么？ | **同一 base→full SFT** 与 **同一 base→mask SFT** | 数据顺序、监督 token、有效 batch、更新精度、学习率、训练步数、选择与推理协议 |
| 从已训练 full 模型适配 mask 是否有效？ | **full SFT→mask 继续训练** 与 **full SFT→full 继续训练** | 相同起点和新增训练预算 |
| 熵门控 RL 是否有效？ | 同一 SFT 起点的普通全 token RL 与熵门控 RL，另保留无 RL 的 SFT | rollout、reward、组大小、采样、mask、优化器、KL 和预算 |

不能把 full 的 1 轮与 mask 的 3 轮直接比较后将全部差异归因于 attention。主分析同时报告共同训练步数的结果；各自最佳 checkpoint 作为“相同选择预算下”的另一组结果。若某一组提前失败，只比较双方都完成的共同阶段，并单独报告失败本身。

同样，若 mask 从 full SFT 权重继续训练，仅与原 base 比较会混入额外训练收益。上表的 full→full 延长训练对照应一并保留。初轮 seed=0 是工程对照；正式方法结论应在配对随机种子上复核。

## 6. 本次改动怎样延续到 KV mask SFT 与熵 RL

### 共享的参数与 token 契约

- **精度：**SFT 与 RL 更新都保持 FP32 常驻参数/Adam 状态，计算可使用 BF16；生成模型统一使用生产推理 dtype。分布式、CPU offload 或 ZeRO 的变化必须重新验证更新与保存恢复。
- **位置：**预测 label[j] 的统计属于 query[j−1]。音频/reference 边界、绝对位置、样本边界、padding、EOS 使用同一元数据定义。
- **类型：**正文、时间戳、speaker、EOS 与跨类型边界 token 分开记录。训练文本可用 tokenizer offset 映射；rollout 必须对应原始 generated IDs 的增量字节/文本跨度，不能重新分词后假定 token 位置不变。无法可靠归类的位置显式标记。
- **概率：**分块计算完整词表的 FP32 logsumexp、目标 log-probability 和熵，只保存逐 token 标量；不能从一个 sampled-token log-probability 反推词表熵。普通 SFT 仍给所有有效 assistant token 相同的 CE 权重，类型和熵仅作观测。
- **验收：**分块统计与密集参照比较数值和梯度；检查点重载后比较 logits；DDP 使用全局有效 token 分母。后续 RL 的零选中 token、全零 advantage 等情况也必须正常同步。

### Mask 与 rollout

KV mask 只改变输出历史的可见集合，完整音频/指令 reference 始终保留，future 始终不可见。full 模式必须是同一契约的合法极限。动态规则只读生成当时已有状态；利用当前目标标签或当前尚未算出的熵决定同一步窗口会造成泄漏或循环依赖。

初版保存 reference + k_max 缓存。窗口缩小再扩大时，不能假定已经物理淘汰的 KV 自动回来；若重算，应记录成本。训练重算、缓存生成、old-policy log-probability 与当前策略重放都使用相同规则和绝对位置。

RL 初版使用匹配的 Transformers 模型生成与重放。将 mask SFT 接到仍使用 full attention 的 rollout 引擎，需要先实现并核验该引擎的 mask 语义，不能直接视为同一策略。

### 熵门控专有部分

固定温度与统计分布定义，区分未处理 logits 的模型熵和采样分布熵。明确按全体输出还是按类型分层取高熵位置，明确跨卡/梯度累积的统计总体、分位点 ties 和损失分母。不能把每卡各自 top 20% 称为全局 top 20%。

第一组 RL 对照保持普通 GRPO 与熵门控版本的 reward、KL 路由和输出长度分母一致；熵门控先只控制策略项，KL 维持全有效输出，作为明示设计。CER/DER advantage 和正文/结构路由另行定义。窗口 mask 与策略 loss gate 是两个独立模块。

本次回放显示循环可以跨越高低不同的熵区间。若熵门控漏掉低熵循环位置，应先记录其比例并做消融，不能通过在 full attention 基线中预先加入反重复训练来掩盖它。

## 7. 正式启动前的最后验收与预算

以下内容属于正式执行的前置检查，**本轮小实验尚未完成这些验收**：

1. 新入口使用独立参数 dtype 开关；核对固定源码、数据/权重 hash 和实际 Trainer/optimizer dtype。
2. 4 卡 DDP、FP32 更新配置上，完成包含最长 116,527-token 会议的全局 batch 更新，检查梯度、GPU 显存及 CPU 内存余量。
3. 同一个全局 batch，对比单卡累积 4 与 DDP4 的 loss/梯度；不能用不同数据或不同分母比较。
4. 保存、卸载、重载并继续一步，确认 FP32 参数和状态、调度器 402 步总长度、数据顺序与每个 rank RNG 延续。
5. 在固定完整音频前缀上检查导出 BF16 推理与保存重载结果，冻结验证和生产解析版本。

前次每组完整 26 场 dev 约用 4.3–6.2 GPU 小时；在当时分配下最长 worker 约 1.15–2.38 小时。采用三个全量验证节点，是在发现失稳和评估成本之间的具体折中。

规划上可为训练预留约 5–7 小时、三次全量 dev 约 3.5–7 小时，总计约 9–15 小时，另计排队与最终 test。此为参考前次运行和短实验的预算估算；CPU offload 改为全 rank、最长样本和实际四卡吞吐均需在第一阶段重新测量。最终测试在模型选择冻结后执行；历史 base 预测可复用准确率，但新的性能比较需要说明计时硬件与运行条件。

若修正精度后仍在验证集发生灾难性重复，先根据中间检查点定位出现阶段，再从同一 base 做学习率或 warmup 的单因素短对照。进一步的声学约束干预、冻结编码器、DITTO/unlikelihood 均以独立实验编号加入，并在 full 与 mask 对照中对称使用。当前不预设它们一定必要。
